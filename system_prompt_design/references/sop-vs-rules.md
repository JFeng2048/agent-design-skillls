# 流程驱动 vs 规则堆砌：系统提示词的“组织方式”

给新员工一份上百条零散规则的手册，没有流程图也没有优先级说明，即使是最聪明的人也会困惑：多条规则同时适用时如何选择？未覆盖的情况如何处理？

模型在训练中学习了人类的语言与思维模式，因此**降低人类认知负担的方法对模型同样有效**。消融实验显示：保留全部规则内容但打乱组织结构、去掉标题层次、拆散有序流程，会导致任务成功率下降超过 30%，模型频繁违反关键业务规则。这说明“对人类友好的信息组织方式，对模型同样友好”。

## 1. 诊断：规则堆砌的信号

出现以下任一现象，说明当前提示词是规则堆砌：

- 模型在多个适用规则间随机摇摆（同一输入多次运行结果不一致）。
- 模型跳过前置步骤直接执行核心动作（典型：未验证身份就退款）。
- 模型询问“规则没说这种情况怎么办”。
- 规则数量持续增长但违规率未下降。
- 规则之间存在隐含顺序（“先验证再执行”），却按并列条目排列。

## 2. 改写目标：编号 SOP

每一步都必须写清五要素：

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| 触发条件 | 什么情况下进入这一步 | 收到退款请求时 |
| 前置状态 | 进入本步时必须已满足的条件 | 身份已验证（Step 1 完成） |
| 动作 | 具体做什么 | 查询最近 90 天订单 |
| 产出 | 完成后得到什么 | 订单列表 + 可退金额区间 |
| 失败分支 | 失败时怎么办 | 未找到订单 → 说明并停止，不进入退款流程 |

```markdown
<file_processing_sop>
Step 1: 校验
  触发：任何文件读取或写入请求
  动作：检查路径是否存在且可访问
  产出：可访问性结论
  失败分支：不存在 → 报错并停止，禁止尝试创建（除非用户明确要求）
  ↓
Step 2: 分类
  触发：校验通过
  动作：按扩展名与内容判定文件类型
  产出：类型标签
  失败分支：无法判定 → 询问用户，禁止默认按文本处理
  ↓
Step 3: 预处理
  触发：类型判定完成
  动作：配置文件 → 先备份；超过 1MB → 分块流式处理
  ↓
Step 4: 执行
  触发：预处理完成
  动作：按文件类型执行核心逻辑
  ↓
Step 5: 校验
  动作：确认产物完整性与可读性
  失败分支：校验失败 → 回滚到备份并报告
</file_processing_sop>
```

## 3. 步骤之间的连线必须显式

模型需要知道**当前在哪一步、下一步去哪**。写法要求：
- 步骤之间显式标注流转关系（`↓`、`→ 进入 Step N`、`满足条件则跳至 Step N`）。
- 条件跳转必须给判断条件：`成功率 ≥ 60% → Step 3；< 30% → 拒绝并说明`。
- 禁止无终点的循环；允许重试但必须写最大次数与兜底出口。

## 4. 决策优先级：把冲突裁决写进流程

多规则冲突时，模型需要一个明确的裁决顺序。两种表达方式：

```markdown
<priority_rules>
- 安全与合规条款 > 业务硬约束 > 流程步骤 > 输出风格偏好
- 用户当轮明确指令可覆盖输出风格偏好，但 NEVER 覆盖安全条款与业务硬约束
- 用户指令与本文件冲突时 → 说明冲突点，按本文件执行并告知原因
</priority_rules>
```

```markdown
<escalation>
- 规则未覆盖的新情况：采取最保守可逆动作，并向用户说明假设
- 涉及金钱、删除、法律后果：停止并请求用户确认
- 连续两次同类失败：停止重试，输出已收集信息与建议
</escalation>
```

## 5. 异常分支清单（每个流程都要覆盖）

为每一步逐项检查：

- **输入缺失**：必要参数不全 → 询问最少的必要信息（一次不超过 2 个问题）。
- **执行失败**：工具报错 → 按重试上限处理，超过则降级或停止。
- **权限不足**：需要更高权限 → 说明并请求授权，不尝试绕过。
- **副作用不可逆**：删除、支付、外发 → 先确认后执行。
- **结果不确定**：无法判定成功与否 → 报告状态，不谎报完成。
- **超时/超限**：达到预算或时间上限 → 输出已有成果并说明未完成部分。

## 6. 流程粒度控制

- 步骤数量控制在 3-7 步；超过则拆成子流程（子流程同样要有编号与终止条件）。
- 单步动作超过 3 个子动作 → 拆步骤。
- 高频任务写完整 SOP；低频任务可只写关键约束。
- 主流程写详细，异常分支写清单（避免长尾异常把主流程淹没）。

## 7. 从规则堆砌迁移的操作步骤

1. 列出所有规则，按主题聚类。
2. 找出规则的隐含顺序（有“必须先…再…”关系的串成链）。
3. 确定流程入口：每类任务从哪个步骤开始。
4. 补齐每一步的失败分支。
5. 单独抽出优先级裁决与兜底条款。
6. 删除被流程覆盖的重复表述（同一事实在两处出现容易不一致）。
7. 用 `scripts/lint_prompt.py` 检查 SOP 结构完整性。

## 8. 自检

- [ ] 每类任务都有编号 SOP，且入口明确
- [ ] 每步都有触发条件、动作、产出、失败分支
- [ ] 步骤之间的流转与跳转条件显式写出
- [ ] 有全局优先级裁决条款
- [ ] 有未覆盖情况的兜底与升级路径
- [ ] 不可逆操作前存在用户确认步骤
- [ ] 无循环流程；重试有上限与出口
