# 工具定义的设计

工具定义（API 请求中的 `tools` 字段）是除系统提示词外另一个重要的**静态组成部分**。工具定义质量直接决定 Agent 使用工具的准确性——可以把它看作给新员工的操作手册：好的描述能让从未使用过该工具的人立即正确使用，并避免常见错误。

消融实验数据：保留函数签名与参数定义、但移除全部描述性文本，工具调用错误率上升 45%，Agent 频繁传入无效参数值或误解参数含义。**描述不是装饰，是功能。**

## 1. 描述必须包含四类信息

以 Claude Code 的工具定义为参照，每个工具描述都精心设计了四类内容：

| 信息类型 | 作用 | 示例 |
| --- | --- | --- |
| 使用边界 | 防止误用与越界 | “NEVER invoke grep or rg as a Bash command” |
| 具体示例 | 消除参数歧义 | `timezone: 'America/New_York'` |
| 性能提示 | 减少往返次数 | “Batch your tool calls together” |
| 协作关系 | 约束工具间顺序 | “Use the Read tool at least once before editing” |

模板见 `assets/tool_schema_template.md`。检查方式：对每个工具自问“从没用过它的人能否一次用对？”

## 2. 参数描述要写语义与格式

- 描述**格式与取值域**：`ISO 8601 时区，如 'America/New_York'`、`1-100 的整数`。
- 描述**缺省行为**：不传会怎样、传空字符串会怎样。
- 明确**互斥与依赖**：`exact=true` 时 `replacements` MUST 为空。
- 给出**最小可用示例**：一个真实取值，胜过三行解释。
- 对自由文本字段说明期望内容，避免模型塞入整篇文档。

## 3. 错误处理写进描述

描述中显式写出失败语义，模型才能正确重试或降级：

- `Error: not found` → 路径不存在，禁止自动创建（除非用户要求）
- `Error: timeout` → 最多重试 2 次，间隔递增
- 不可逆操作 → 必须在描述中标注 `Requires confirmation`

## 4. 工具数量治理：渐进式披露

基础模式是**静态前缀**：系统提示词 + 工具定义随请求发送，由服务商与前缀一起缓存。工具少时这是最优方案。但工具数量膨胀（尤其接入 MCP 后）会撑爆上下文并稀释注意力，因此工具定义也在向 Skills 式的**渐进式披露**演进，且已是 API 层原生能力而非框架补丁：

| 提供方 | 机制 | 说明 |
| --- | --- | --- |
| OpenAI Responses API | `tool_search` + `defer_loading: true` | 模型通过 `tool_search_call` → `tool_search_output` 按需加载完整 schema |
| Anthropic | Tool Search（`tool_reference` blocks） | Claude Code 对 MCP 工具默认延迟加载：启动时只注入工具名称与服务器说明 |
| Codex CLI | `tool_search`（BM25 检索） | 非可选特性，默认开启 |

共同点：静态前缀只保留工具**名称与简述**，完整 schema 在模型按需请求后追加到上下文末尾，成为轨迹的一部分。

### 为什么追加到末尾不破坏缓存

这是 KV Cache 前缀性质的直接推论：因果注意力决定每个 token 在每一层的隐状态（以及由它算出的 K、V）只依赖该 token 自身及其之前的 token，与后面的 token 无关。因此在末尾追加新内容**不会改变任何已缓存 token 的 K、V**——新增 schema 只需在首次出现时计算一次（一次性缓存写入），此后就并入不断增长的“前缀”，在后续所有轮次持续命中。

所以这不是“预编译”，而是**只增不改的追加式注入**。

一个常见误解需澄清：“追加到末尾”只发生在工具被发现的那一轮。此后 schema 块就固定在轨迹中的原位置，后续轮次的新消息追加在它之后，它本身成为普通历史消息，而不是每轮都被重新搬运到最新末尾。

### 模型能力约束

该机制要求模型必须在训练中见过“工具定义出现在对话中间”这一模式，这也是它目前只在较新模型（GPT-5.4+、Claude 4.5+ 系列）上支持、自托管开源模型需专门训练的原因。评估模型能力时要把此项纳入选型。

## 5. 治理策略

- 工具数量控制在 20 个以内；超出时按场景分组（文件 / 网络 / 业务 / 通信），每组按需加载。
- 工具职责单一，禁止“万能工具”靠参数分支承担多职责。
- 工具之间建立显式依赖关系（读取 → 修改 → 校验），并在各自描述中交叉引用。
- 统一命名风格：`动词_名词`（`read_file`、`send_email`），避免 `get`/`fetch`/`retrieve` 混用。
