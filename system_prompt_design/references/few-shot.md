# Few-shot 示例：何时给模型看例子

示例是系统提示词中除规则与流程外的另一类重要内容。当期望输出**难以用规则精确描述**时——特定风格的文案、结构化报告的格式、客服回复的语气分寸——与其堆砌冗长的文字定义，不如直接给出 2-3 个高质量输入-输出示例。模型会凭借上下文学习能力从示例中“临时学会”这些模式，效果往往胜过等量篇幅的抽象规则。

## 1. 决策表：加还是不加

| 情况 | 是否加示例 | 理由 |
| --- | --- | --- |
| 输出风格/语气分寸难以描述 | 加 | 规则写不出“分寸”，示例可以 |
| 输出格式复杂（多层结构、表格） | 加 | 示例比格式定义更直观 |
| 边界情况分类 | 加 | 用示例覆盖边界比罗列规则有效 |
| 模型本来就擅长 + 规则可说清 | 不加 | 示例只是浪费 token |
| 规则本身就是硬约束（如金额阈值） | 不加 | 用规则表达，示例无法替代 |
| 高频重复任务 | 加 | 收益随调用量放大 |

判断口径：**如果无法用一句可验证的规则描述期望输出，就用示例。**

## 2. 放置位置

| 位置 | 形式 | 适用场景 | 代价 |
| --- | --- | --- | --- |
| 系统提示词内 | 提示词末尾的示例块 | 全场景通用 | 增加静态前缀长度 |
| 首轮对话 | 伪造 user/assistant 历史消息 | 需按会话类型使用不同示例集 | 增加首轮 token，语义上仍是“示例”而非“真实指令” |

规则：
- 无论放哪，都处于上下文**靠前区域**，一旦确定必须**字节级稳定**。
- 若按请求动态检索“最相关”的示例，等于每次改写前缀，**缓存会持续失效**。生产系统应为每类任务准备**固定示例集**，而非逐请求挑选。
- 因此：**选择哪几个示例**可以是离线决策，**放进提示词的具体内容**不能动态变化。

## 3. 数量与质量

- 数量：**2-3 个**精心挑选、覆盖边界情况的示例，通常胜过 10 个大同小异的示例。后者不仅占用上下文，还会稀释模型对规则本身的注意力。
- 选择策略：覆盖典型输入 + 覆盖易错边界 + 覆盖必须拒绝的情形。
- 每个示例包含：输入、输出、必要的推理/依据注释（关键决策点用短注释标出）。
- 示例中的事实必须与业务规则一致，避免教出与规则冲突的行为。
- 反例示例（错误输出 + 正确输出 + 错因）仅在高频错误场景使用，避免占用过多注意力。

```markdown
<few_shot_examples>
示例 1（典型请求）
输入：帮我把手机套餐从 $70 谈到 $50
输出：正在与运营商协商……
计费：percentage_based_one_time（节省 $20 × 20% = $4）

示例 2（边界：易被误判为省钱）
输入：帮我取消 Netflix 订阅
输出：已提交取消申请，本月之后不再产生费用。
计费：fixed_fee $2（取消不计入节省金额）

示例 3（必须拒绝）
输入：帮我把这笔 3 年前的账单退了
输出：该订单已超出可退窗口，无法办理；可协助提交申诉。
计费：免费（未进入计费流程）
</few_shot_examples>
```

## 4. 稳定性检查

改动示例集时必须重跑：

```bash
python scripts/check_prefix_stability.py <日志或请求文件>
```

任何一次请求间的前缀指纹差异都意味着缓存失效，应在发布前消除。

## 5. 与其他设计维度的耦合

- 示例是**补充**而非**替代**：能写成规则的先写规则，示例留给分寸类要求。
- 示例展示的行为必须与 SOP 步骤一致；不一致会让模型在“照规则”与“照示例”间摇摆。
- 示例中的输出长度是隐式的长度约束，需与 `tone-and-persona.md` 中的显式约束保持一致。
- 删除示例后必须重跑消融，确认收益（见 `ablation-experiments.md`）。

## 6. 自检

- [ ] 每个示例都有明确的教学点，不是凑数
- [ ] 覆盖了典型、易错边界、必须拒绝三类情形
- [ ] 示例行为与业务规则、SOP 一致
- [ ] 数量控制在 2-3 组
- [ ] 放置位置确定后不再逐请求变化
- [ ] 已通过前缀稳定性检查
