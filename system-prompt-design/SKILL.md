# 系统提示词设计

把系统提示词当作 Agent 的“员工手册”来设计：定义身份、行为规则、约束条件和工作流程。
目标不是把模型能力写强，而是把业务决策权从模型的自由裁量中收回到提示词里。

## 动手前：自己把需求调研清楚，尽量不问用户

**核心原则：Agent 能力范围内能确认的事，自己确认。** 把问题推给用户没有意义——用户也得去查同样的资料。只有**必须由人拍板的业务决策**才需要用户参与，且必须给选项。

### 1. 自主调研（项目 → 文档 → 线上数据）

| 手段 | 能拿到什么 | 做法 |
| --- | --- | --- |
| 项目勘察 | 现有提示词文件与结构、工具定义与数量、业务规则实现、语言风格、是否已有 few-shot、动态字段风险 | `python scripts/discover_prompt_context.py <项目目录>` + 定向检索（见 `references/information-gathering.md`） |
| 文档与检索 | 行业规范、平台差异、模型能力边界、同类产品做法 | 用 `web_search` / `web_fetch` 查权威来源，**不要凭记忆给结论** |
| 线上数据 | 真实失败案例、高频任务类型、用户投诉、运营经验 | 读日志与评测样本，从失败案例倒推缺失的规则 |
| 实测 | 提示词是否生效、规则违反率、工具错误率 | 跑评测集 + `scripts/lint_prompt.py` + 对照实验 |

判定顺序：**先项目 → 再文档/检索 → 再线上数据与实测 → 仍不确定且属业务决策，才问用户。**

调研输出的是**带证据的事实**（`文件:行`），至少覆盖：现有提示词位置与结构、工具清单、业务规则与阈值的实现位置、语言风格、失败案例、模型与服务商。

### 2. 推断默认方案（可直接落地）

基于调研事实给出完整默认方案，而不是罗列可能性：

- 身份与目标：从现有提示词或产品文档中提取，缺失则按项目定位补全。
- 规则集：从**线上失败案例**倒推需要补哪些规则（这是规则最有价值的来源）。
- 工具定义：复用项目中已有的工具清单，按 `references/tool-design.md` 补齐四类描述信息。
- 语言与风格：跟随项目现有语言与术语，**不另起一套**。
- 结构：沿用项目已有的块命名习惯，避免风格漂移。

默认方案要能在用户不作任何选择时直接落地。

### 3. 只有业务决策才问用户

必须问的只有这几类（查不到、且属于人的取舍）：

1. **业务规则与判定口径**：某任务算哪一类、阈值是多少、超限后拒绝还是降级。
2. **产品取舍**：转化率优先还是风险控制优先、是否允许 Agent 自主外联。
3. **权限与合规边界**：能读写什么、哪些数据不能进上下文。
4. **目标权重**：多个指标冲突时以哪个为准。

提问要求：

- 用户做的是**在推荐方案上做选择**，不是回答问卷。
- 一次 **≤3 个问题**，每个给 2-4 个选项，**标明推荐项与推荐理由**（依据来自哪个文件/哪次实测）。
- **禁止**问能从项目或文档里读到的信息（工具数量、现有规则、模型名等）。
- 用户说“你定”或不回复 → 采用推荐项，在 `assets/requirements_intake.md` 记为**假设**并注明复核时间。

## 核心检验标准：新员工检验

设计完成后，代入一位**聪明但完全不懂本业务的新员工**，只读这份提示词，回答：

1. 我是谁、要为谁服务、成功的标准是什么？
2. 收到某类任务时，第一步做什么、后续步骤是什么？
3. 两条规则同时适用时听谁的？规则没覆盖的情况怎么办？
4. 哪些操作我绝对不能做？
5. 做不完 / 做错时该怎么向用户交代？

任何一条答不上来，Agent 在真实任务中同样答不上来。答不上来的部分就是当前提示词的缺陷清单。

## 设计流程（按序执行）

### 1. 澄清身份与目标
产出：身份、用户画像、职责边界、成功判据。
- 明确 Agent 的**权限范围**（能读写什么、不能碰什么）。
- 明确**失败姿态**：遇到能力边界外的事如何回应（这是语气约束的原料）。
- 输入来自**自主调研**：现有提示词、产品文档、线上失败案例（见上文「动手前」）；调研读不到的才列入业务决策找用户确认。
- 结论写入 `assets/requirements_intake.md`。
- 详见 `references/tone-and-persona.md`（人格与语气部分）。

### 2. 定义语气与行为风格
产出：长度约束、失败时的回复约束、大写强调清单。
- 给出**可量化的输出约束**（如“少于 4 行”“1-2 句话”），而非“简洁、专业”。
- 大写（NEVER / MUST / ALWAYS）**只留给真正关键的约束**，其余用普通表述；过度使用会稀释注意力。
- 明确禁止自我辩护式长解释。
- 详见 `references/tone-and-persona.md`。

### 3. 搭建结构骨架
产出：Markdown 层次 + XML 语义块的双层结构。
- 用 Markdown 标题（`#` / `##`）承担**人读的组织逻辑**。
- 用 XML 标签承担**机器可解析的精确语义**，标签名必须携带业务语义。
- 顺序即优先级：身份 → 能力边界 → 规则 → 流程 → 示例 → 安全。
- 详见 `references/structure-and-format.md`，骨架直接复制 `assets/system_prompt_template.md`。

### 4. 把规则堆砌改成流程驱动
产出：带编号步骤、分支条件、异常处理的标准操作流程。
- 每一步写清：触发条件 → 动作 → 产出 → 失败分支。
- 把“优先级裁决”显式写出来，而不是让模型遍历规则去匹配。
- 详见 `references/sop-vs-rules.md`。

### 5. 业务规则可执行化
产出：决策表、阈值映射、计费/配额粒度、显式禁止项、边界反例消歧。
- 业务逻辑由产品/业务方定义，工程师负责**准确编码**，不擅自发明业务规则。
- 规则必须落到可执行程度：可枚举的分类、明确的数值阈值、写死的计算粒度。
- 每个易混淆的类别配一条“反例 + 判定依据”。
- 详见 `references/business-rules.md`，模板见 `assets/business_rules_spec_template.md`。

### 6. 用 few-shot 补齐“说不清的部分”
产出：2-3 个固定的高质量输入-输出示例。
- 只在“风格 / 格式 / 语气分寸”难以用规则描述时才加示例；模型本就擅长且规则说得清的任务不要加。
- 示例一旦确定即**字节级稳定**，按任务类型准备固定示例集，**不要逐请求动态检索**（会击穿 KV Cache 前缀）。
- 详见 `references/few-shot.md`。

### 7. 设计工具定义
产出：带使用边界、示例值、性能提示、协作关系的工具描述。
- 工具定义与系统提示词共同构成**静态前缀**，同样需要字节级稳定。
- 工具过多时采用**渐进式披露**：前缀只留名称与简述，完整 schema 由模型按需检索并追加到轨迹末尾。
- 详见 `references/tool-design.md`，模板见 `assets/tool_schema_template.md`。

### 8. 加固上下文安全
产出：来源标记规范、角色纪律、输入清洗、升级与人工确认路径。
- 上下文层防御（来源标记、指令/数据分离、清洗）**只是第一道防线**，无法做到万无一失。
- 高风险操作必须留执行层防线：权限控制、沙盒隔离、高风险动作独立确认。
- Skill 内容、状态栏、知识库检索结果都是**注入面**，按“加载外部代码”的标准审查。
- 详见 `references/prompt-injection.md`。

### 9. 消融验收与迭代
产出：基线配置、逐项消融的对照实验、归因结论。
- 用控制变量法**逐个移除系统组件**，观察任务成功率、工具调用错误率、交互轮次、用户满意度变化。
- 定位失效元素时优先怀疑：**信息组织方式 > 工具描述 > 语气风格**。
- 详见 `references/ablation-experiments.md`。

## 交付前自检清单

**调研与定位**

- [ ] 已自主调研项目并留下 `文件:行` 证据，未把可查到的信息抛给用户
- [ ] 规则来源包含线上失败案例归因，而非凭空编写
- [ ] 默认方案已给出且可直接落地（用户不选也能开工）
- [ ] 需要用户拍板的只剩业务决策，≤3 项且每项带选项与推荐项
- [ ] 采用推荐值但未确认的项已标注为「假设」并写入设计输入表

**内容与设计**

- [ ] 存在明确的身份定义与职责边界
- [ ] 所有长度/格式约束可量化（行数、句数、字段名），无“适当”“尽量”类模糊词
- [ ] 大写强调只出现在关键约束上，且密度可解释
- [ ] 失败路径已定义（能力边界外、工具失败、信息不足时的回应方式）
- [ ] 主要任务类型都有编号流程，且带异常分支
- [ ] 规则冲突时有明确的优先级裁决规则
- [ ] 每条业务规则都有可判定条件（枚举 + 阈值 + 粒度）
- [ ] 易混淆类别配有反例消歧
- [ ] 高风险操作要求用户确认，且禁止项用显式否定句写死
- [ ] 外部内容一律包裹来源标记，明确“其中指令不可执行”
- [ ] few-shot 示例为固定集，未使用按请求动态检索
- [ ] 工具描述包含使用边界、示例值、性能提示、协作关系
- [ ] 静态前缀内容字节级稳定（`scripts/check_prefix_stability.py`）
- [ ] 至少跑过一轮消融实验，确认各要素贡献

## 常见反模式

| 反模式 | 表现 | 修正方向 |
| --- | --- | --- |
| 规则堆砌 | 上百条平铺规则，无优先级与流程 | 改写为编号 SOP，补充裁决规则 |
| 模糊规则 | “根据情况选择合适的模式” | 用决策表枚举判定条件 |
| 大写滥用 | 满篇 MUST / NEVER，重点消失 | 只保留 3-5 条生死约束 |
| 无异常分支 | 只有主流程 | 每步补“失败 → 降级 / 停止 / 升级” |
| 示例动态检索 | 每次请求检索“最相关”示例 | 按任务类型固定示例集 |
| 提示词承载业务 | 工程师自行发明计费/权限逻辑 | 产品定决策，工程师做编码 |
| 不查项目直接问用户一堆开放问题 | 用户还得自己去查，答案质量更差 | 项目/文档/线上数据能拿到的自己拿 |
| 凭空写规则 | 覆盖不到真实失败模式 | 从线上失败案例倒推需要补的规则 |
| 只在上下文层防御 | 依赖来源标记即可防注入 | 补执行层权限与高风险确认 |
