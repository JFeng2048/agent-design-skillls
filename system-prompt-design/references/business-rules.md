# 业务规则细化：系统提示词的“内容”

业务规则细化是生产级 Agent 系统中最容易被忽视、却最关键的环节。**这不是技术问题，而是产品设计问题**，需要产品经理的深度参与：优秀 Agent 公司的提示词通常由产品经理基于线上数据、用户反馈与运营经验设计规则定义，工程师负责把规则准确编码进提示词（格式正确、结构清晰），**不应擅自决定业务逻辑**。

设计哲学：大模型的优势在于遵循复杂指令、从长上下文提取信息，但**不应在业务规则制定上被赋予过多自由裁量权**。用清晰的操作框架解放模型的认知资源，让它专注真正需要思考的部分——就像好的新人培训不是“你很聪明，自己看着办”，而是给出明确 SOP，让人在框架内发挥能力。

## 1. 规则必须可判定

一条规则能否被模型稳定执行，取决于它是否可判定。用“三要素”检查每条业务规则：

| 要素 | 要求 | 反例 | 正例 |
| --- | --- | --- | --- |
| 判定条件 | 枚举值或数值阈值 | “任务比较困难” | “成功率估算 < 30%” |
| 判定依据 | 可观测信号 | “客户比较急” | “用户消息含 deadline/紧急/asap 关键词” |
| 动作 | 唯一确定动作 | “适当处理” | “使用固定费用模式，预收 $9，不予退款” |

改写示例（模糊 → 可执行）：

```markdown
<!-- 反例：模糊，导致行为极不稳定 -->
根据任务情况选择合适的计费类型。

<!-- 正例：枚举 + 阈值 + 唯一动作 -->
按省钱提成（percentage_based_one_time）：
  仅适用于通过谈判降低现有账单的场景，需实际使用谈判话术。
  NEVER 适用于退款与服务取消，此类场景一律使用 fixed_fee。
成功率估算：
  ≥ 60% → 使用可退款模式（percentage_based_one_time）
  30% ~ 60% → 使用 fixed_fee 可退款模式
  < 30% → 直接拒绝任务，并说明成功率过低
```

## 2. 决策表：把分类争议变成可查表

当“某任务属于哪一类”存在争议时，用决策表替代口头描述。列 = 输入信号，行 = 判定结果。

```markdown
<计费模式判定>
| 任务信号 | 是否使用谈判 | 涉及金额来源 | 计费模式 |
| 降低现有账单（如砍价、投诉减免） | 是 | 现有账单减少 | percentage_based_one_time |
| 取消订阅（未来不再产生费用） | 否 | 无（不基于现有账单） | fixed_fee |
| 退款（取回已支付款项） | 否 | 无（不基于现有账单） | fixed_fee，退还时免收服务费 |
| 预订餐厅等纯服务型请求 | 否 | 无 | fixed_fee，按复杂度分级 |
| 成功率估算 < 30% | — | — | 拒绝任务，不受理 |
</计费模式判定>
```

关键消歧规则要显式写出：
- **“省钱”只基于现有账单计算**，NEVER 把“避免未来涨价”计入节省。
- 取消订阅是否算省钱：不算，因为它只影响未来支出。写死这一条，否则模型会自行扩展定义。
- 退款不是省钱，是取回本属于用户的资金。

## 3. 数值与计算要写死粒度

模型擅长语义判断，不擅长精确算账。所有涉及计算的地方都要给公式、粒度、舍入与上下限。

```markdown
<计费计算规范>
- 电话通话：每分钟 $0.05，按实际分钟数向上取整到整分钟
- 汇总后四舍五入到最接近的整数美元
- 金额低于 $1 时按 $1 计收
- 节省金额仅按现有账单差额计算，禁止计入假设性的未来涨价
- 佣金 = 节省金额 × 20%，四舍五入到最接近的整数美元
</计费计算规范>
```

补齐以下要素：计费粒度（每分钟 / 每千 token）、舍入方向、封顶与保底、异常值处理（极小额、极大额、超时）。

## 4. 分步评估：把“判断”拆成可核对的流程

任何需要估算或打分的判断（成功率、优先级、紧急度、置信度），都要写成固定流程，避免模型凭感觉给分。

```markdown
<成功率估算流程>
Step 1: 商家历史数据 → 该商家同类任务成功率基线（缺失则用默认值 50%）
Step 2: 用户配合度 → 用户是否提供了必要凭证（是 +15%，否 -20%）
Step 3: 诉求复杂度 → 涉及多方协调 +10%，涉及法律/监管 -25%
Step 4: 时间窗口 → 距截止时间 < 24h -15%
Step 5: 汇总并对照阈值 → ≥60% 可退款模式；30%~60% fixed_fee；<30% 拒绝
每一步的调整幅度写死，禁止跳过步骤直接给最终概率。
</成功率估算流程>
```

## 5. 禁止项要带替代方案

只写禁令而不给路径，模型会退化为模糊应付或硬闯。格式：**禁止 + 替代动作**。

```markdown
<禁止项与替代>
- NEVER 使用 percentage_based_one_time 处理退款和服务取消 → 改用 fixed_fee
- NEVER 在未读取文件内容前写入 → 先调用读取工具，再执行写入
- NEVER 假设用户已授权外发邮件 → 先展示邮件正文并获得确认
- NEVER 静默失败 → 返回失败原因与已完成的步骤
</禁止项与替代>
```

## 6. 边界反例消歧

对每个易混淆类别，配一条“易误判输入 + 正确判定”，直接写进提示词。

```markdown
<消歧案例>
- 输入：“帮我退掉上个月买的衣服”
  判定：fixed_fee（取回已支付款项），不是省钱提成场景
- 输入：“帮我取消 Netflix 订阅”
  判定：fixed_fee；不计入节省金额，因不减少任何现有账单
- 输入：“帮我把手机套餐从 $70 谈到 $50”
  判定：percentage_based_one_time，需实际使用谈判策略
- 输入：“下周要用的保龄球馆，帮我订个场”
  判定：fixed_fee 服务型任务，按复杂度收费
</消歧案例>
```

## 7. 规则冲突与未覆盖情况

- 冲突裁决写进优先级条款（见 `sop-vs-rules.md`）。
- 未覆盖情况的默认动作是**最保守可逆动作**，并要求向用户说明假设。
- 明确**升级路径**：什么情况必须停下来问人（涉及金钱、删除、法律后果、多方协调失败）。

## 8. 迭代机制

规则不是一次写完的：
- 从线上失败案例、用户投诉、运营数据中提取新规则。
- 每次只加一条规则并做一次消融，确认这条规则带来收益而非噪声。
- 定期清理被覆盖的旧规则，防止规则集膨胀导致遵循率下降。
- 规则变更记录在 `assets/business_rules_spec_template.md` 的变更日志中，便于回滚。

## 9. 自检

- [ ] 每条规则含判定条件、判定依据、唯一动作
- [ ] 存在关键分类的决策表
- [ ] 易混淆类别配了反例消歧
- [ ] 所有计算写明粒度、舍入、上下限
- [ ] 所有估算类判断写成固定分步流程
- [ ] 每条禁止项都带替代动作
- [ ] “节省”“退款”“取消”等关键词在文件内有唯一定义
- [ ] 有规则冲突裁决与未覆盖兜底
- [ ] 业务决策来源已标注（产品/业务方确认），未由工程师擅自发明
