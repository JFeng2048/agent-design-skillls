# 结构化提示：系统提示词的“格式”

现代大语言模型对结构化输入的敏感度显著高于人类直觉——训练数据中充满结构化内容，标签结构本身就是可被利用的先验。结构化的目标有两个：**人读得懂层次**、**模型读得准语义**。

## 1. 双层结构：Markdown 管组织，XML 管语义

单用一种都有缺口：

- 纯文本（`当前目录：/Users/project/src`）：模型需要额外推断冒号前后的语义关系。
- 纯 XML：结构精确但人类可读性差，评审与维护成本高。
- 纯 Markdown：可读性好，但块级语义边界弱，模型难以判断“这段管辖到哪里”。

推荐组合：Markdown 标题表达层次与管辖范围，XML 标签表达块级精确语义。

```markdown
# 工具使用规范

## 文件操作
<file_operation>
- 读取文件前必须先确认路径存在
- 写入文件前必须先备份原文件
</file_operation>

## 网络请求
<network_request>
- 超时时间设置为 30 秒
- 失败后最多重试 3 次
</network_request>
```

- `#` / `##` 让人一眼看出层次、归属与优先级顺序。
- `<file_operation>` / `<network_request>` 让模型明确“这个块讲文件操作”“这个块讲网络请求”，语义精确、不外溢。

## 2. 标签命名规范

标签名是给模型读的**语义信号**，命名质量直接决定块的识别准确率。

规则：
1. 用 `snake_case` 的业务语义名，不用排版名。
   - 好：`<refund_policy>`、`<success_rate_estimation>`、`<working_directory>`
   - 差：`<div>`、`<info>`、`<section1>`、`<box>`、`<text>`
2. 一个标签只承载**一个语义主题**；主题不同的规则分到不同标签。
3. 需要被程序解析的块，把关键参数写进属性：
   ```markdown
   <external_content source="webpage" trust="untrusted">
   ```
4. 同名标签在整个提示词中含义一致，禁止复用同一标签表达不同规则。
5. 嵌套不超过两层；层级过深时模型定位成本上升。

## 3. 顺序即优先级

模型按提示词的书写顺序分配注意力，前部权重更高。因此推荐骨架顺序：

```
1. 身份与目标（persona / mission）
2. 能力边界与权限（capabilities / permissions）
3. 硬约束（hard_constraints）——红线条目
4. 业务规则（按主题分块）
5. 操作流程（SOP，带步骤与异常分支）
6. 输出规范（长度、结构、语气细则）
7. few-shot 示例
8. 安全与注入防御（external_content 规范）
9. 兜底：未覆盖情况如何处理
```

把**兜底规则放最后**是有意为之：模型在遇到未匹配情况时更接近结尾内容。
需要立即可见的内容（红线、当前任务目标）靠前放，需要兜底的靠后放。

## 4. 标题层次的卫生要求

- 全文只保留**一个** H1（业务域名称），H2 为一级分区，H3 为二级分区。
- 不跳级（不出现 H1 → H3）。
- 标题名用名词短语（`退款政策`）而非动词短语（`退款政策怎么写`），便于模型识别为**区域标签**。
- 同一分区内的信息量控制在 5-10 条细则；超过则拆子块或下沉到 reference/Skill 按需加载。

## 5. 段落写法

- 每条细则**一行一条**，以动词开头（“检查…”“禁止…”“返回…”）。
- 条件在前，动作在后：`当 X 时 → 执行 Y；否则执行 Z`。
- 数值、字段名、枚举值用 `反引号` 包裹，减少歧义。
- 避免跨条目指代（“如上所述”“上一条提到的规则”），改为显式重复关键条件。

反例与正例对照：

```markdown
<!-- 反例：条件与动作分离、指代含糊 -->
处理退款时需要注意，不要使用按提成计费，除非是砍价场景。

<!-- 正例：条件 → 动作 → 例外，一行一条 -->
按提成计费仅适用于通过谈判降低现有账单的场景。
退款与取消服务 NEVER 使用按提成计费，一律使用固定费用。
```

## 6. 用结构承载优先级

结构不仅组织内容，还表达规则的裁决顺序。三种可用机制：

1. **位置**：靠前的分区优先级更高（配合第 3 节顺序）。
2. **标签语义**：用 `<override>`、`<fallback>` 等标签标明覆盖关系。
   ```markdown
   <fallback>
   本节规则仅在本文件未覆盖时生效；与上文任何冲突条款冲突时以本节为准
   </fallback>
   ```
3. **显式裁决条款**：在多规则可能同时适用处直接写出优先级。
   ```markdown
   <priority>
   规则冲突时按以下顺序裁决：安全条款 > 业务硬约束 > 通用偏好 > 输出风格
   </priority>
   ```

## 7. 静态前缀视角的结构约束

系统提示词是 KV Cache 前缀的一部分，意味着：
- 提示词与工具定义共同构成**静态前缀**，内容必须**字节级稳定**。
- 禁止在提示词中插入每次请求变化的字段（时间戳、用户 ID、当日日期、随机排序）。动态信息应放在**紧随其后的 user 消息**中。
- 检查方法：`scripts/check_prefix_stability.py`。

需要动态化的内容（当前工作目录、当前时间、用户偏好）也不要写进提示词，改为在首条 user 消息中以带来源标记的 XML 注入：

```markdown
<session_context source="system_runtime" trust="trusted">
<working_directory>/Users/project/src</working_directory>
<current_date>2026-10-08</current_date>
</session_context>
```

## 8. 结构自检

- [ ] 标签名全部具备业务语义，无排版类命名
- [ ] 每个标签只承载一个主题，无同标签异义
- [ ] 单一 H1，无标题跳级
- [ ] 每条细则一行、动词开头、条件在前
- [ ] 多规则冲突处有显式裁决条款
- [ ] 兜底规则位于末尾
- [ ] 提示词中不存在每次请求变化的动态字段
