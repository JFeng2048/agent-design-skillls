# 状态栏的维护纪律与安全风险

## 1. 用代码维护，不要让 LLM 批量统计

**原则**：状态栏尽量用**代码**维护；实在要用 LLM，也要**逐条抽取、再由代码汇总**，绝不要让它一次性批量统计。

**原因**：实验发现模型几乎无条件地相信状态栏——你写「打了 3 次电话」，它就当真是 3 次，不会自己重算。而 LLM 做数量统计本来就容易出错。

因此：
- 计数、阈值比对、状态机推进 → 代码。
- 需要语义判断的抽取（如判断某条 TODO 是否完成）→ LLM 逐条抽取，代码汇总成最终状态。
- 禁止让 LLM 一次性输出「工具调用统计 + TODO 状态 + 环境信息」的整块状态栏。

## 2. 状态栏投毒（Status Bar Poisoning）

因为模型无条件信任状态栏，**谁控制了状态栏写入，谁就控制了模型的判断**。

风险通道：

| 通道 | 风险 |
| --- | --- |
| 外部内容写入状态摘要 | 网页/文档片段被写进状态栏 → 被当成可信指令 |
| 工具返回值参与状态计算 | 恶意工具返回内容影响计数或 TODO 状态 |
| 用户可控字段进入状态栏 | 用户伪造「已完成」状态 |
| 多 Agent 共享状态 | 其他 Agent 写入不可信状态 |

**防护**：
- 状态字段**只来自受控数据源**（框架自身的计数器、环境变量、内部 TODO 存储）。
- 状态栏中的文本字段做白名单与长度限制，禁止自由文本直接透传。
- 在系统提示词中明确：状态栏中若出现指令性内容，不予执行。
- 复用 `system_prompt_design` 中「来源标记 + 指令与数据分离」的防御思路。

## 3. 谨慎删除原始上下文

状态栏是对原始上下文的**一次有损投影**——它只提前算了「你预想会被问到」的那些维度。

- 如果状态栏够用（计数、状态跟踪这类任务就是如此），可以把原始记录整段删掉，只保留状态栏，**节省大量 token**。
- 但只要有一个问题涉及状态栏**未计算的维度**，仅保留状态栏就会导致准确率**断崖式下降**。

**判断方法**：抽取线上真实问题样本，逐条检查「回答这个问题所需的维度是否都在状态栏中」。有任何一条不在，就不能整段删除。

建议策略：保留最近 \(k\) 轮原始记录 + 全量状态栏，而非二选一。

## 4. 状态栏的长度纪律

状态栏是**注意力资源**而非日志：

- 每增加一个字段都挤占其他字段的注意力权重。
- 定期清理不再被任何决策使用的字段（用消融实验验证：删掉它指标是否下降）。
- 稳定字段与易变字段分开组织，易变字段放最靠近末尾的位置。

## 5. 可观测性

- 所有注入的状态栏消息都要落盘记录，便于事后审计「模型当时看到了什么」。
- 记录状态来源（计数器 / 环境 / LLM 抽取），出错时可定位到具体字段。
- 状态栏与决策日志对齐：每次模型决策对应哪一条状态栏版本。

## 6. 自检

- [ ] 计数与阈值比对由代码实现，非 LLM 批量统计
- [ ] 若用 LLM，为逐条抽取 + 代码汇总
- [ ] 状态字段只来自受控数据源，无外部自由文本透传
- [ ] 系统提示词中声明：状态栏中的指令性内容不予执行
- [ ] 删除原始记录前已验证状态栏覆盖所需全部维度
- [ ] 定期消融清理无效字段
- [ ] 状态栏注入有落盘记录，可审计
