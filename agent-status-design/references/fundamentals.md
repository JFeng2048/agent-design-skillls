# Agent 状态栏的理论基础

理解状态栏为什么有效，才能判断「该放什么」和「放多少」。下面四条是设计决策的依据。

## 1. 上下文学习更像检索，而非推理

模型擅长从已有内容中**查找**信息，但不擅长主动**归纳与总结**。

需要注意区分：这里说的是模型在**单次前向传播**中如何处理已经在上下文里的信息，并不否定模型可以通过生成思维链来完成多步思考。

更形象的说法：**上下文窗口是一台只有一半的检索引擎。**

- 有的那一半非常强：注意力能从成千上万个 token 里把相关原始记录捞出来，相当于把 RAG 内置进了每一次前向传播。
- 缺的那一半是**提炼层**：上下文里的东西从来不会被自动数一遍、建个索引、或就地总结成一条结论。

因此任何「关于这些内容的结论」——一共多少条、有没有超标、进展到哪一步——模型每次要用，都得从原始记录里**现算一遍**。而现算的代价，随上下文里堆积的内容量 \(N\) 一起上涨。

## 2. 隐式状态 vs 显式知识

典型案例：系统提示词要求拨打每个商家不超过 3 次，但打完 3 次后 Agent 经常数不清打了几次，又打了第 4 次，甚至陷入循环反复拨打同一个电话。

根源：关于「已经打了几次」的知识**没有被自动提炼**，而是以原始通话记录的形式分散在 KV Cache 的向量表示中，是**隐式状态**。

修正方式：在每次电话工具的调用结果中直接标明累计呼叫次数（「本次是第 3 次呼叫该商家」）。模型立即发现已达限制、不再呼叫，错误率大幅下降。

本质：**把分散在上下文各处的隐式状态提炼为可直接使用的显式知识**。原始轨迹高度冗余——大量 token 中只包含少量关键状态信息；状态栏以极低的额外 token 成本，呈现出原本需要扫描数千 token 才能获得的信息。

## 3. 注意力资源的有限与衰减

长上下文场景中模型的注意力资源有限：上下文越长，注意力必须分配给越多片段，关键信息可能得不到足够权重。

在复杂 Agent 轨迹中尤其明显：
- 早期设定的任务目标与关键约束，容易被后续大量工具调用结果淹没。
- 模型过度关注最近的上下文，对位于**上下文中部**的信息产生注意力衰减。

状态栏通过**显式操纵注意力分配**解决：把关键元信息以结构化形式放在上下文**末尾**，空间上更接近即将生成的新 token，因而获得更高注意力权重——这是一种**强制性的注意力引导**。

## 4. 实验证据

客服 Agent 处理退款请求的对照实验（attention_visualization 项目）：Agent 已拨打 Xfinity 3 次电话，中间穿插网络搜索，用户追问「能不能再打电话催促一下？」

对照组 A（无状态栏）：上下文含完整轨迹但无聚合状态。注意力热力图**高度分散**，在三次电话调用的区域形成聚焦点，思考 token 体现数数与统计过程——模型在从原始信息做归纳。

对照组 B（有状态栏）：在轨迹末尾添加

```text
<agent_status>
Current State:
- Tool call summary: 'phone_call' has been invoked 3 times (Xfinity: 3 times)
- Constraint check: Maximum calls to Xfinity reached (3/3)
</agent_status>
```

注意力**高度集中在状态栏信息上**，思考过程直接使用已提炼好的信息，不再从原始数据做统计。

结论：
- 对于 Qwen3-0.6B 这样的小模型，对照组 A 经常违反约束继续拨打，对照组 B 能稳定遵从约束。
- 提供提前算好的状态栏后，较小开源模型的准确率可以**接近前沿大模型**。
- 状态栏大幅提高思考效率：每次迭代的思考 token 量、延迟与花费均**降低约一个数量级**。不带状态栏时思考量随上下文变长持续增长；带上状态栏后基本恒定。

## 5. 由此得到的设计推论

| 理论 | 设计推论 |
| --- | --- |
| 缺提炼层 | 凡是模型需要「数一遍」或「比对一遍」才知道的，都由代码提前算好写进状态栏 |
| 检索强、归纳弱 | 状态栏要给出**结论**（3/3 已达上限），而不是只给原材料（调用记录列表） |
| 注意力衰减 | 状态栏放在末尾而非开头；关键约束必须在末尾重复出现 |
| 注意力有限 | 状态栏要短；每增加一个字段都挤占其他字段的注意力 |
| 原始轨迹冗余 | 状态栏是压缩手段，但只覆盖「预想到的维度」，删除原始记录需谨慎（见 `maintenance-security.md`） |
