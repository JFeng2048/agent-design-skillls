# 状态更新的两种实现与缓存代价

「追加不破坏缓存」只在**单次注入**时成立。状态是会变的——下一轮 TODO 完成一项、工具计数加一次，状态消息就过时了。因此必须选择更新策略。

## 实现一：每轮替换（Replace）

**做法**：每次 API 调用前，从消息列表中**移除**上一轮的状态消息，在末尾**追加**最新状态。

**优点**：上下文中只有一份状态，永远最新；模型不会读到陈旧状态，无歧义。

**代价**：移除旧状态会使其位置之后的**所有缓存失效**——这与「动态时间戳」是同一个失效机制。区别在于状态消息位于上下文**末尾**，失效范围只覆盖上次注入后新增的消息（通常是一轮），整个前缀仍可复用。

**适用**：状态较大、更新频繁、轨迹很长、陈旧状态造成的歧义成本高。

## 实现二：持久追加（Append）

**做法**：状态消息一旦注入就**永久留在轨迹中**，每轮只在末尾追加新状态。

**实例**：Claude Code 的 `<system-reminder>` 采用这种方式——历史状态消息保留在会话记录（transcript）中，从不删改。

**优点**：对缓存**完全友好**——所有消息只追加、不修改，前缀始终稳定。

**代价**：陈旧状态在上下文中累积，既占用 token，也要求模型自己关注「最新一条」状态而忽略已过时的旧状态。

**适用**：状态很小、两次更新间产生的消息很多、会话长度受控。

## 取舍模型

设：
- \(S\)：每条状态消息的 token 数
- \(R\)：两次更新之间新增后缀的 token 数
- \(N\)：预计更新次数
- \(\alpha\)：缓存输入单价相对普通输入的倍数（缓存更便宜，故 \(\alpha < 1\)）

忽略两种方案共有的成本：

\[
C_{\text{替换}} \approx (N-1)(1-\alpha)R
\]

\[
C_{\text{追加}} \approx \alpha S \cdot \frac{N(N-1)}{2}
\]

比较可得：当 \(\alpha S N / 2 < (1-\alpha) R\) 时倾向**实现二（持久追加）**，否则倾向**实现一（每轮替换）**。

> 该估算未计入上下文占用与陈旧状态带来的歧义，实际选择还应结合服务商的缓存计费与实测命中率。建议用 `scripts/cache_cost_estimator.py` 代入自己的数值，并做一次实测校准。

## 决策表（定性版）

| 条件 | 倾向策略 | 理由 |
| --- | --- | --- |
| 状态很小 \(S\)、轮间新增很多 \(R\) 大 | 持久追加 | 保留旧状态通常比反复重算长后缀便宜 |
| 状态较大 \(S\)、更新频繁 \(N\) 大 | 每轮替换 | 只使上次注入后的短后缀失效，避免陈旧状态累积 |
| 轨迹很长 | 每轮替换 | 陈旧状态的 token 与歧义成本随长度放大 |
| 会话长度受控、轮数少 | 持久追加 | 缓存完全友好，实现简单 |
| 小模型 / 易被陈旧状态误导 | 每轮替换 | 歧义成本高于缓存收益 |
| 要求轨迹可完整复现审计 | 持久追加 | 只增不改的历史天然可审计 |

## 混合策略

两种策略可以组合使用：

1. **分区更新**：易变字段（时间、计数）每轮替换；稳定字段（用户原始诉求、任务目标）随事件追加一次后不再变动。
2. **阈值切换**：前 \(k\) 轮用追加（缓存友好），状态累积超过阈值后切换为替换。
3. **稀疏替换**：不是每轮都替换，而是每 \(m\) 轮替换一次，把失效次数降到 \(N/m\)。

混合策略的成本需要重新建模，建议直接用实测的缓存命中率校准。

## 与压缩的配合

状态栏本身是上下文压缩的一种手段（见 `maintenance-security.md`）。当轨迹过长时：

- 先确认状态栏覆盖了决策所需的**全部维度**；
- 再把已被状态栏提炼的**原始记录整段删除**；
- 删除操作只影响被删段落之后的缓存，需与更新策略一并测算。
