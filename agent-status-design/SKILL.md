# Agent 状态栏设计（编码实现指导）

提示工程给的是**静态指令**，Agent 执行时还需要**动态感知自身状态与任务进展**。把这些信息整理成结构化摘要注入上下文，就是 Agent 状态栏。

类比操作系统的状态栏：手机顶部始终显示时间、电量、信号、通知数——不是 App 主界面，但随时瞥一眼就掌握设备状态。Agent 状态栏对模型起完全相同的作用：它不是对话主体内容（不属于用户消息、模型输出或工具结果），而是框架在**上下文末尾持续注入**的状态摘要。

## 本 skill 的定位：编码实现指导，不是提示词模板

**这不是「生成一份提示词模板」的 skill，而是「指导你在代码里把状态栏机制实现出来」的 skill。**

| 维度 | 本 skill 关注 | 不属于本 skill |
| --- | --- | --- |
| 产出 | 状态字段与数据结构、计数器与约束检查的实现、TODO 存储与工具、注入时机与消息结构、更新策略、审计日志 | 系统提示词的规则与流程撰写 |
| 载体 | 框架代码（Harness 侧的状态维护与消息拼装） | 一段写死的提示词文本 |
| 关键约束 | 状态必须由代码计算，不交给 LLM 统计 | 用提示词让模型「自己数清楚」 |
| 相邻技能 | 状态栏里「规则怎么表达」属 `system-prompt-design` | — |

配套关系：系统提示词写「每个商家最多拨打 3 次」（规则），状态栏由代码写出「已拨打 Xfinity 3/3」（事实）。前者是 `system-prompt-design` 的产出，后者是本 skill 的产出。

`assets/` 下的文件是**代码的输出格式约定与填写表单**，不是要塞进 system prompt 的模板。

## 核心检验标准：瞥一眼检验

把状态栏单独抽出来给模型看，它能否**不扫描原始轨迹**就回答：

1. 这个工具调用了几次？是否已达上限？
2. TODO 还剩几项？当前在哪一项？
3. 现在几点？工作目录在哪？什么系统？
4. 上次操作为什么失败？建议怎么修？
5. 用户的原始诉求是什么（而非当前局部子任务）？

任何一条答不上来，模型就得从原始记录里现算一遍——代价随上下文长度增长，且容易算错。**答不上来的维度就是状态栏需要补的字段。**

## 为什么必须做状态栏：理论基础

- **上下文学习更像检索而非推理**：模型擅长从已有内容里查找，不擅长主动归纳统计。上下文窗口是「只有一半的检索引擎」——检索很强，但缺「提炼层」：不会自动数一遍、建索引或就地总结。
- **每次现算的代价随内容量增长**：「已打几次电话」的知识以原始通话记录形式分散在上下文中，模型每次决策都要扫描重新统计，效率低且错误率高。
- **注意力衰减**：上下文变长后，早期设定的目标与关键约束易被后续大量工具结果淹没，模型过度关注最近内容。
- **强制性注意力引导**：把关键元信息结构化放在上下文**末尾**，空间上最接近即将生成的新 token，因此获得最高注意力权重。

效果（对照实验）：给模型一条提前算好的状态栏后，小模型（如 Qwen3-0.6B）从「经常违反 3 次上限继续拨打」变为「稳定遵从约束」，准确率接近前沿大模型；每次迭代的思考 token 量、延迟与花费降低约**一个数量级**，且思考量不再随上下文增长而增长。

## 动手前：自己把信息找齐，尽量不问用户

**核心原则：Agent 能力范围内能确认的事，自己确认。** 把问题推给用户没有意义——用户也得去查同样的资料，只是多一轮往返。只有**必须由人拍板的业务决策**才需要用户参与，且必须给选项。

### 1. 自主获取信息（项目 → 文档 → 实测）

| 手段 | 能拿到什么 | 做法 |
| --- | --- | --- |
| 项目勘察 | 工具清单、已有计数器/TODO/状态栏实现、消息拼装位置、约束阈值、模型与服务商、语言风格 | `python scripts/discover_context.py <项目目录> --trace trace.jsonl` |
| 文档与网页检索 | 服务商缓存计费与 α、缓存命中规则、模型是否支持 `tool_search`、平台差异 | 用 `web_search` / `web_fetch` 查官方文档，**不要凭记忆给数值** |
| 本地实测 | S / R / N、缓存命中率、思考 token 量、延迟与成本 | 跑样本轨迹 + `scripts/cache_cost_estimator.py` + 埋点 |
| 对照实验 | 某项技术是否真的有效 | 有/无该技术的 A/B（见 `references/techniques.md`） |

判定顺序：**先项目 → 再文档/网页 → 再实测 → 仍不确定且属业务决策，才问用户。** 详见 `references/information-gathering.md`。

勘察输出的是**带证据的事实**（`文件:行`），至少覆盖：工具清单与数量、是否已有状态栏/计数器/TODO、消息拼装位置、约束与阈值、模型与服务商、轮数与轮间 token。

### 2. 推断默认方案（给出可直接落地的推荐）

基于勘察事实给出**完整默认方案**，而不是罗列可能性：

- 字段集：按「症状 → 技术」映射选出（见 `references/techniques.md`），每个字段注明依据（哪个文件/哪类失败案例）。
- 计数维度：默认按项目中已有的**调用参数里最常重复的字段**分组（勘察得到），而非一律全局计数。
- 更新策略：用勘察得到的 S/R/N 代入 `scripts/cache_cost_estimator.py` 算出结论，作为默认值。
- 注入点：直接定位到勘察找到的消息拼装处，给出改动位置。

默认方案要能在用户不作任何选择时直接落地。

### 3. 只有业务决策才问用户

必须问的只有这几类（查不到、且属于人的取舍）：

1. **业务规则与阈值**：调用上限是多少、超限后拒绝还是降级。
2. **产品取舍**：体验优先还是成本优先（直接影响更新策略与压缩力度）。
3. **权限与合规边界**：哪些数据不能进上下文、是否需审计留痕。
4. **目标权重**：多指标冲突时以哪个为准。

提问要求：

- 用户做的是**在推荐方案上做选择**，不是回答问卷。
- 一次 **≤3 个问题**，每个给 2-4 个选项，**标明推荐项与推荐理由**（依据来自哪个文件/哪次实测）。
- **禁止**问能从项目或文档里读到的信息（工具数量、模型名、现有限制、α 等）。
- 用户说「你定」或不回复 → 采用推荐项，在 `assets/requirements_intake.md` 记为**假设**并注明复核时间。

### 4. 记录

勘察事实、推断结论与待确认项写入 `assets/requirements_intake.md`（含证据列 `文件:行`），作为设计输入与对齐留痕。

## 设计流程（按序执行）

### 1. 确定状态维度
产出：状态字段清单 + 每个字段的数据来源（哪个计数器、哪个环境变量）。
- 从失败案例倒推：模型因为「不知道什么」而做错了决策？
- 只放**决策真正依赖**的元信息，避免状态栏膨胀成上下文负担。
- 详见 `references/status-content.md`。

### 2. 设计工具调用计数与约束
产出：计数维度（全局 / 按目标分组）、上限、超限时的显式标注。
- 在工具**返回结果中直接标注累计次数**（如「本次是第 3 次呼叫该商家」），模型看到计数即触发模式识别。
- 约束检查写进状态栏：`已达上限 (3/3)`，而不是让模型自己比对。
- 用 `scripts/status_ledger.py` 从轨迹中统计并生成状态片段。

### 3. 设计 TODO 列表结构
产出：TODO 项 schema（唯一 ID、内容、状态、时间戳）+ 两个专用工具。
- 状态枚举：`pending` / `in_progress` / `completed` / `cancelled`。
- 提供 `rewrite_todo_list` 与 `update_todo_status` 两个工具，通过「复述」操纵注意力。
- 外部记忆作用：实验显示启用 TODO 后平均 15 次迭代完成任务，禁用需 21 次且经常遗漏子任务。
- 模板见 `assets/todo_tool_schema.md`。

### 4. 设计事件的侧信道信息
产出：随事件追加的元数据（精确时间、地理位置、距上次回复的时间间隔等）。
- 侧信道信息**随对应事件一起追加**，不在主数据通道里，但帮助模型理解时序与环境背景。
- 时间戳用 `[2025-09-14 10:30:45]` 前缀加在用户消息与工具响应上。

### 5. 设计环境观察摘要
产出：系统时间、工作目录、OS、Shell、Python 版本等动态环境信息。
- 工作目录跟踪尤其关键：执行 `cd` 后自动更新，确保后续操作在正确上下文。
- OS 信息让模型做出平台相关决策（Linux 用 apt、macOS 用 brew）。

### 6. 设计详细错误信息格式
产出：四层错误结构（类型与描述、完整参数 JSON、调用栈、针对性修复建议）。
- 修复建议要具体：`FileNotFoundError` → 验证路径、检查工作目录、使用绝对路径。
- 启用后错误场景找到替代方案的成功率从 60% 提升到 95%，从盲目重试转为有针对性解决。
- 详见 `references/techniques.md`。

### 7. 确定注入位置与消息结构
产出：状态栏消息的 role、位置、包裹标签。
- 在 API 层面作为**一条 `user` 角色的消息插入到上下文末尾**，不修改 system 消息（否则破坏 KV Cache 前缀）。
- 用 `<agent_status>` 标签包裹，标明这是框架生成的元信息而非真实用户输入。
- 这是「动态信息追加末尾、静态信息保持不动」原则的直接应用。
- 详见 `references/injection-position.md`。

### 8. 选择状态更新实现
产出：替换 or 追加的决策结论 + 成本估算。
- **实现一 每轮替换**：移除上一轮状态消息、末尾追加最新状态。上下文中永远只有一份最新状态；代价是使上次注入后新增的后缀缓存失效（通常只有一轮）。
- **实现二 持久追加**：状态消息永不删改（Claude Code 的 `system-reminder` 即如此）。对缓存完全友好；代价是陈旧状态累积，占用 token 且要求模型关注最新一条。
- 用 `scripts/cache_cost_estimator.py` 按 `S / R / N / α` 估算分界点，决策表见 `assets/update_strategy_decision.md`。

### 9. 确立维护纪律
产出：状态维护方式、原始上下文保留策略、投毒防护。
- 状态栏**尽量用代码维护**；确需 LLM 时逐条抽取后由代码汇总，绝不让它一次性批量统计。
- 模型几乎无条件相信状态栏：写「打了 3 次」它就当真，不会自己重算——因此**状态栏投毒**是真实风险。
- 状态栏是有损投影：只提前算了「预想会被问到」的维度。只有状态栏够用时才整段删除原始记录，否则准确率断崖式下降。
- 详见 `references/maintenance-security.md`。

### 10. 验收
产出：对照实验结论（有/无状态栏）。
- 指标：约束遵从率、完成任务所需迭代次数、思考 token 量、延迟与成本、遗漏子任务率。
- 逐步消融五种技术，观察单独与组合的效果差异（见 `references/techniques.md` 的涌现效应）。

## 交付前自检清单

**需求与定位**

- [ ] 已自主勘察项目并留下 `文件:行` 证据，未把可查到的信息抛给用户
- [ ] α、模型缓存规则等数值来自文档检索，非凭记忆
- [ ] S / R / N 来自样本或实测，非拍脑袋
- [ ] 默认方案已给出且可直接落地（用户不选也能开工）
- [ ] 需要用户拍板的只剩业务决策，≤3 项且每项带选项与推荐项
- [ ] 采用推荐值但未确认的项已标注为「假设」并写入设计输入表
- [ ] 交付物是代码实现方案，而非一份提示词模板

**状态内容**

- [ ] 状态栏能回答「瞥一眼检验」的全部 5 个问题
- [ ] 每个字段都能说明「缺了它会做错什么决定」
- [ ] 工具调用计数在**工具返回结果中**直接标注，而非只写在系统提示词
- [ ] 约束以 `已用/上限` 形式显式写出，超限有明确禁止动作
- [ ] TODO 项含唯一 ID 与状态枚举，并提供 rewrite / update 工具
- [ ] 侧信道信息随事件追加，时间戳不写入系统提示词
- [ ] 环境摘要含时间、工作目录、OS，工作目录会随 cd 更新
- [ ] 错误信息包含四层：类型、完整参数 JSON、调用栈、修复建议

**工程实现**

- [ ] 计数、阈值比对、状态机推进由代码实现，不依赖 LLM 统计
- [ ] 注入点位于消息拼装层，以独立消息追加到末尾
- [ ] 状态栏以 user 角色消息插入**上下文末尾**，未修改 system 消息
- [ ] 状态栏用 XML 标签包裹，标明其为框架生成的元信息
- [ ] 更新策略已用成本脚本测算，结论有数值依据
- [ ] 每次注入的状态快照已落盘，可按轮次回放
- [ ] 有状态栏投毒防护：状态字段只来自受控数据源
- [ ] 未整段删除原始上下文，或已确认状态栏覆盖所需全部维度

## 常见反模式

| 反模式 | 后果 | 修正 |
| --- | --- | --- |
| 把状态写进 system 消息 | 破坏 KV Cache 前缀，缓存持续失效 | 改为末尾追加的 user 角色消息 |
| 时间戳放进系统提示词 | 每轮改写前缀 | 时间戳随事件追加 |
| 让模型自己数调用次数 | 数错、超限、陷入循环 | 代码计数并在结果中标注 |
| 用 LLM 一次性批量统计状态 | 统计出错且模型无条件采信 | 代码维护，或逐条抽取 + 代码汇总 |
| 状态栏塞满无关字段 | 稀释关键信息的注意力 | 只保留决策真正依赖的维度 |
| 每轮重写整个状态栏且体积很大 | 缓存失效范围扩大 | 用成本脚本选择替换或追加 |
| 只保留状态栏、删除原始记录 | 未覆盖维度的问题准确率断崖下降 | 确认覆盖后再压缩 |
| 状态栏内容可被外部内容污染 | 投毒：模型无条件相信 | 状态只取受控数据源 |
| 不查项目直接问用户一堆开放问题 | 用户还得自己去查，多一轮往返且答案未必准 | 项目/文档/实测能拿到的自己拿 |
| 凭记忆给 α 与模型能力 | 成本算错、用了模型不支持的机制 | 文档检索核实，不确定就标注为假设 |
| 把状态栏当提示词写死 | 状态无法随运行更新，等于没有状态栏 | 状态由代码计算，只把渲染结果注入 |
